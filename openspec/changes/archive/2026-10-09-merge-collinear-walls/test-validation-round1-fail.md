## Находки

### F1. Свободный конец не защищён для конца `a` (в рамках; критерий a и d)

Спека: «начало новой стены лежит у конца E — `a` или `b` — и этот конец свободен». Мутант M11b: проверка занятости выполняется только для `b`, у `a` всегда считается свободным.

Почему выживает: MW-8, 8b, 8c проверяют занятый конец `b` с продолжением у `b`. MW-8d занимает конец `a`, но продолжение ставится у `b` (мутант не затронут). MW-8e занимает `b` и продолжает `a` (свободный). Продолжения у занятого `a` нет ни в одном тесте. Достижимо пользователем: продолжить в обратную сторону стену, у начала которой стоит угол или стык, и получить слияние вместо угла. Это нарушает предложение спеки и поведение «Конец занят».

Тесты, которые надо добавить (проверены в копии: проходят на эталоне, убивают M11b):

```ts
it("MW-8f: конец a занят стыком, продолжение у a — слияния нет", () => {
  const f = w(0, 0, 0, 300, "F")
  expect(mergeContinuation(sceneOf([E(), f]), N(-10, 0, -400, 0)).kind).toBe("none")
})

it("MW-8g: конец a занят пересекающей стеной (T/крест на торце), продолжение у a — слияния нет", () => {
  const g = w(0, -100, 0, 100, "G")
  expect(mergeContinuation(sceneOf([E(), g]), N(-10, 0, -400, 0)).kind).toBe("none")
})
```

### F2. Нарушение проёма проверяется для удлинённой стены без учёта переприкрепления (в рамках; критерий d)

Спека: нарушение проёма ДОЛЖНО проверяться для удлинённой стены; элементы остаются на месте («Продолжение с проёмом не нарушает его»). Мутант M23: `violatesDoorways` вызывается с исходным списком элементов (привязка `b`, расстояние прежнее). Тогда элемент, привязанный к удлиняемому концу, «уезжает» вместе с концом, и слияние ложно блокируется, если там стоит другая стена.

Почему выживает: ни в одном тесте у элемента с привязкой к удлиняемому концу нет на пути «уехавшего» положения другой стены. MW-11 и MW-18 используют свободную сцену, MW-12 проверяет проём другой стены.

Достижимо: дверь у конца `b` стены E, продолжение проходит через другую стену, пересекающую путь старой привязки. Реальный результат по спеке: слияние (дверь на месте). Мутант вернёт `blocked`, и пользователь не сможет продолжить стену.

Тест, который надо добавить (проверен в копии: проходит на эталоне, убивает M23):

```ts
it("MW-11b: дверь с привязкой b у удлиняемого конца, на пути «уехавшего» положения стоит другая стена — слияние выполнено", () => {
  const v = w(750, -200, 750, 200, "V")

  const r = mergeContinuation(scene, N(510, 0, 900, 0))

  }

```

## Примечания (вне рамок, на вердикт не влияют)

- N1. Выбор среди нескольких кандидаток (M24, M25). Спека молчит; наименьший `s`, при равенстве первая в массиве, зафиксировано только в design D2. Тестировщик не может вывести ожидаемое из спеки. Если решение важно, его надо перенести в спеку, а затем покрыть тестом.
- N2. Стена E нулевой длины в сцене (M40). Спека не требует; design D2 говорит «невырожденная ось». Без пропуска получаются NaN в новой вершине. Реально нулевую стену, видимо, чистит существующая очистка, поэтому недостижимо через интерфейс.
- N3. MW-13 («Одна запись истории») проверяет `record`/`undoEntry` из `history.ts` на сцене, которую подготовил сам тест, а не обвязку `commitPoint`. Он не ловит ошибку в `main.ts` (например, две записи истории или запись не до слияния). Это принятое ограничение test-plan («Подключение в main.ts — вручную»). Условие: ручная проверка цепочки, отмены и повтора должна быть записана в `test-suite.md` и в TODO.md, как для `auto-dimensions`.
- N4. M27 эквивалентен исходной реализации (поведение не отличается), не требует теста.
- N5. Неоднозначность design: D1 в первом предложении называет возврат `Scene | null`, а в конце — дискриминированный результат `none | blocked | merged`. Тесты и test-plan следуют второму. Для читателя это противоречие, на тесты не влияет.
- N6. Для спека-неоднозначностей, которые тестировщик не может разрешить, кроме N1, нет.
