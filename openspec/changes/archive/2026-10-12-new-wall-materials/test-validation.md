## Integration Behavior

Загрузка документа → тип стены → пометки → остатки «Монтажа» → страница PDF и легенда — покрыто. Рисование стены → записанные операции холста/страницы PDF — покрыто. Образцы легенды сравниваются с чертежом той же страницы (`toEqual` по структурному облику) — сильная интеграционная защита. Подложка «Демонтажа» с бетонной и снесённой стенами (холст и PDF) — покрыто. Разметка панели против каталога — покрыто (без DOM, чтением файла).

## Implementation Independence

Тесты измеряют наблюдаемую геометрию (углы, шаги, порядок операций, цвета, габариты), точные числа не зашиты, кроме неизменных значений «Кирпича» (3 мм/0,25 мм) и красной штриховки (3 мм) — это регрессия существующего поведения. Принадлежность образца легенды столбцу/чертежу теперь определяется по середине габаритов операции, а не по каждой точке: референс с тайлами «Дерева», выходящими за образец (в том числе вариант с тайлом 40×26 мм и вариант «один штрих на тайл»), проходит весь набор (F5 закрыта). Замечание: `isHatchOp` в PDF-тестах отбирает штриховку по эвристике «толщина 0,05–0,3 мм и наклон/пунктир» — реализация с волосяной «Блоков» тоньше 0,05 мм упала бы на «каждый материал штрихуется» (ложное падение, допустимо и документировано).

## Assertion Strength

Сильные: попарная различимость рисунков по подписи (углы/пунктир/заливка/шаг/толщина/узор), порядок заливка → штрихи → контур, габариты заливки против габаритов контура (в том числе у наклонной стены), контраст заливки с `ink` ≥ 3 и с `paper` ≥ 1,1, решётки через `onLattice`, образец = чертёж через `toEqual`, шаг красной штриховки `toBeCloseTo(3, 2)`. Вакуумных циклов не найдено: перед циклами по возможно пустым наборам стоят `length > 0` (в тесте «штриховка рисуется цветом ink схемы» защиты `length` внутри нет, но соседний тест «каждый материал реально штрихуется» гарантирует непустоту). Проверка старых тестов против HEAD: усилений больше, чем ослаблений; единственные ослабления — `isHatchWidth` (теперь «тоньше или равна штриховке кирпича, > 0,05 мм» вместо «равна»; нужно для тонких «Блоков»/«ГКЛ», толщины закреплены новыми тестами WM-H2/H5/L6) и `inColumn/inChart` (середина вместо всех точек; закрыто F5); LG-9/LG-15 пересчитаны на «Кирпич»/«ГКЛ»/«Демонтируемая стена» с тем же смыслом; DM-27 «concrete сносится» заменён на blocks/gkl и «бетон не сносится».

Оценка переноса ручной проверки в `tasks.md`: ПРИЕМЛЕМО при условии, что чек-лист появится в `tasks.md` до реализации как отдельная обязательная задача и будет пройден на шаге verify/до архивации. Основания: в проекте нет DOM-окружения, у `main.ts` нет UI-тестов, правило UI требует повторить существующие паттерны (разметка остаётся статической, цикл идёт по `MATERIALS`, код стрелок менять не нужно), а составляющая «разметка = каталог» теперь автоматизирована. Чек-лист должен содержать ровно:

1. Панель «Стена»: пять образцов в порядке «Блоки, Кирпич, Бетон, ГКЛ, Дерево», у каждого мини-превью штриховки своего материала и подпись; старых «Железобетон» и «Дерево (вдоль)» нет; при открытии приложения активен «Кирпич» (WM-U1, U2, U8).
2. Клик по каждому образцу: он выделяется, остальные снимаются, следующая нарисованная стена и превью — штриховкой этого материала (WM-U1).
3. Стрелка вниз при невыделенном: «Блоки → Кирпич → Бетон → ГКЛ → Дерево → Блоки»; стрелка вверх — обратно, с «Блоков» на «Дерево» (WM-U3, U4).
4. Панель «Стена» закрыта: стрелки переключают материал, панель остаётся закрытой, следующая стена — новой штриховкой (WM-U5).
5. Выделена стена (и отдельно — размер): стрелки материал не переключают (WM-U6).
6. Фокус в поле толщины: стрелки меняют число, материал не меняется (WM-U7).
