## Context

Сейчас (до change):

- `src/main.ts`, обработчик `pointerdown` холста: при любом инструменте, кроме ластика, `pressPick` отдаёт
  цель «элемент» (`case "doorway"`), и `doorwayTool.pressDoorway(p)` выделяет элемент и начинает
  перетаскивание. Нажатие ставит `suppressClick`, поэтому следующий `click` установку не выполняет.
  Активный инструмент (`tool`) при этом не меняется.
- `setTool(next)` сбрасывает всё состояние инструмента, **включая выделение** (спека: активация инструмента
  снимает выделение). Поэтому «снять инструмент вручную» после выделения двери выделение теряет, и клик в
  зону направления (`pressZone`, срабатывает только при выделенной одной двери) попадает в пустоту.
- `src/doorway/openings-group.ts`: состояние группы (`current`, `active`, `panelOpen`); `active: "other"`
  означает «активен инструмент вне группы», в том числе «нет инструмента».
- Выделение элемента не открывает панели и не меняет `tool` (прежнее требование `canvas-app`).

## Goals / Non-Goals

**Goals:**
- Выделение существующего элемента стены при активном инструменте установки («Проём», «Дверь», «Окно»)
  переводит приложение в состояние «нет инструмента, элемент выделен».
- Перетаскивание, начатое тем же нажатием, продолжается и записывается в историю как раньше.

**Non-Goals:**
- Менять `setTool` (активация и ручная деактивация по-прежнему снимают выделение).
- Менять поведение инструментов «Стена», «Размер», «Линейка», «Ластик».
- Менять правку чисел, формат хранения, историю, PDF; деактивировать инструмент после установки новой двери
  (пользователь выбрал оставлять инструмент активным).

## Decisions

**D1. Отдельный переход «выйти из установки, сохранив выделение».** В `main.ts` — функция рядом с
`setTool`, которая: ставит `tool = "none"`, сбрасывает призрак инструментов установки (не их перетаскивание),
закрывает панель группы (`closeOpeningsPanel`), вызывает `syncToolUI` и `redraw`. Выделение, редактор чисел
и `nudgeBurst` она не трогает; `openingsCurrent` не меняется. `setTool("none")` не подходит: он снимает
выделение. Альтернатива — вызвать `setTool("none")` и затем заново выделить элемент: отвергнута, потому что
`setTool` сбрасывает также редактор, `suppressClick` и жесты, а повторное выделение шумит в состоянии.

**D2. Место вызова.** Ветка `case "doorway"` в `pointerdown`: если `pressDoorway(p)` вернул `true` и
`placingTool()` не `null`, вызывается переход D1 — после того как нажатие выделило элемент и начало
перетаскивание. Тип инструмента не проверяется отдельно: `placingTool()` уже равен `null` вне «Проём»,
«Дверь», «Окно». Для «Стена» (и «Размер», «Линейка») вызова нет — их поведение не меняется. Ластик сюда не
попадает (цель «элемент» для него отключена в `pressPick`).

**D2a. Решение — чистая функция перехода.** Весь переход после нажатия на элемент выносится в чистую
функцию рядом с состоянием группы (`src/doorway/openings-group.ts`):

`afterElementPress(state: { tool: Tool; group: GroupState; selected: boolean }): { tool: Tool; group: GroupState }`

где `Tool` — тип инструментов приложения (`"wall" | "dimension" | "doorway" | "door" | "window" | "eraser" |
"ruler" | "none"`, выносится из `main.ts` в тот же модуль), `selected` — нажатие выделило существующий элемент
(результат `pressDoorway`) или правит выделенный (результат `pressNumber` / `pressZone`). Правило: если `selected` и `tool` — `"doorway" | "door" | "window"`, результат —
`tool: "none"`, `group` с `active: "other"`, `panelOpen: false` и прежним `current`; во всех остальных случаях
(не выделено, любой другой инструмент) результат равен входу (тот же `tool` и значение `group`). Функция не
мутирует вход. `main.ts` вызывает её в ветке `case "doorway"` и применяет результат: при смене инструмента —
переход D1. Состояние группы в `main.ts` (`openingsCurrent`, `openingsPanelOpen`) берётся из `group` результата.

**D2b. Правка выделенного при активном инструменте.** Ветка `pointerdown` с `pressNumber`/`pressZone`
(`main.ts`, до `pressPick`) тоже вызывает `afterElementPress` с `selected: true`, когда одно из них вернуло
`true`, и применяет переход D1 при смене инструмента. Порядок: сначала правка/ввод, затем выход из установки,
чтобы поле ввода числа не закрывалось выходом (D1 редактор не трогает). Так же `finishMarquee` вызывает
`afterElementPress` с `selected`, равным «рамка захватила хотя бы один элемент стены»; выделение рамкой
сохраняется целиком.

**D6. Зона направления = прямоугольник ∪ сектор тени.** `doorZoneAt` (`src/doorway/doorway-layout.ts`) для
каждого из четырёх направлений проверяет прямоугольник (как сейчас) и тень: сектор радиуса w вокруг петли
направления между закрытым положением и полотном (угол от `u` к `n` в `[0°, 95°]`) и четырёхугольник полотна
из `doorLeaf` для этого направления. Из направлений, чьи зоны содержат точку, выбирается то, чья петля ближе
к точке (равенство — `a`); для точек прямоугольников это совпадает с прежним правилом «половина двери».
`doorZones` (многоугольники прямоугольников, используется отрисовкой штриховых полотен) не меняется.
Отрисовка тени не меняется.

**D7. Наведение на тень направления.** `SelectionEditing` получает чистый запрос
`hoverDirection(p): DoorDirection | null` (`doorway-tool.ts`): та же очередность, что у нажатия — выделена ровно
одна дверь и нет других выделенных объектов; если под `p` правимое число — `null`; иначе `doorZoneAt`; результат,
совпадающий с текущим направлением двери, — `null`. `RenderOptions` получает `hoverDoorDirection?: DoorDirection |
null`; в `render.ts` при отрисовке трёх штриховых альтернатив направление, равное `hoverDoorDirection`, рисуется
тем же `drawLeaf` без штриха. `main.ts` хранит сырую (непривязанную) мировую точку курсора `hoverWorld`: ставит
её в `pointermove` (до ветвления по инструментам), обнуляет в `pointerleave` и при начале жеста; в `redraw`
вычисляет `hoverDoorDirection` через `selectionEditing.hoverDirection`, кроме инструмента «Ластик». PDF и
невыделенные двери опцию не получают (`opts` пуст).

**D3. Сброс призрака без сброса перетаскивания.** `ElementTool.reset()` обнуляет и призрак, и `drag`, а
перетаскивание уже начато в `pressDoorway`. Поэтому для деактивации нужен сброс только призрака:
у `ElementTool` — метод `clearGhost()`; `reset()` остаётся для `setTool`. Вызов — для всех трёх инструментов
установки (достаточно активного, но единообразнее для всех).

**D4. Состояние группы.** После перехода D2a `group.active` равен `"other"` (кнопка группы не выделена),
`panelOpen` — `false`, `current` — прежний. Кнопка группы далее ведёт себя по `groupButtonClick`
(`active !== current` → текущий инструмент группы активируется и снимает выделение, как в спеке).
Закрытие панели и сохранение `current` определяются только `afterElementPress`, а не отдельными вызовами в
`main.ts`.

**D5. История.** Выход из установки не пишет в историю: запись создаёт только перетаскивание (`endDrag`),
как сейчас.

## Risks / Trade-offs

- Пользователь, ставящий несколько дверей подряд и случайно кликнувший по существующей, теряет активный
  инструмент и должен выбрать его снова — осознанный размен: приложение входит в режим правки.
- Нажатие на элемент при активном инструменте теперь имеет побочный эффект на `tool`; он отражён в спеке
  `doorway` («Выделение проёма кликом») и `canvas-app`, покрыт сценариями и тестами.
- Утверждённые тесты, закрепляющие «выделение не меняет активный инструмент» для инструментов установки
  (если есть), потребуют test-change-request; поиск — в test-plan.md.

## Migration

Нет: хранение, история и PDF не затронуты.
