## Context

Мотивация — `proposal.md` (Why). Сейчас предмет мебели — `Table` (`src/types.ts`), и на нём завязаны: геометрия (`src/furniture/table.ts`), значения панели (`table-params.ts`), жесты (`table-tool.ts`), правка и выбор (`table-edit.ts`), пересечения (`overlap.ts`, вид препятствия `"table"`), цвет (`tableColors` в `furniture-render.ts`), легенда PDF (`legend.ts`, `legend-draw.ts`), хранение (`isTable` в `storage.ts`), история (`FurnitureState` в `history.ts`), панель в `main.ts` и `index.html`. Всё, кроме значений по умолчанию, цвета, записи легенды, слова плашки, иконки и кнопки в панели, от «стола» как вида не зависит.

Форма предмета везде прямоугольник: `clipByRect` в `overlap.ts` строит полуплоскости из углов, `hitTable` проверяет попадание по двум осям, рамка выделения и габариты PDF берут четыре угла.

## Goals / Non-Goals

**Goals:**
- Новый вид одной формы (прямоугольник) добавляется записью каталога и не требует правок логики.
- Поведение пользователя при единственном виде «Стол» не меняется.

**Non-Goals:**
- Не-прямоугольные формы и общая функция `footprint(item)` (решено в explore: вынести, когда появится вид не прямоугольной формы; для выпуклых форм достаточно будет обобщить `clipByRect`, для вогнутых — делить на выпуклые части).
- Разные наборы полей у видов (высота и др.): у всех видов ширина, длина, угол.
- Новые виды (стул, диван) — отдельные changes через скилл `add-furniture-kind`.

## Decisions

**D1. Один тип `FurnitureItem` с `kind`, каталог — данные в одном модуле.**
`FurnitureItem { id, kind, x, y, widthCm, lengthCm, angleDeg }`, `FurnitureKind = "table"`. Каталог `FURNITURE_KINDS` в `src/furniture/furniture-kinds.ts` — константа-запись по виду: `label`, `plaqueWord`, `defaults {widthCm, lengthCm, angleDeg}`, `colors {light, dark: {fill, outline}}`, `icon` (SVG-разметка кнопки). Порядок видов — порядок объявления (`FURNITURE_KIND_ORDER`). Тип `FurnitureKind` выводится из ключей каталога, поэтому `switch` по виду проверяется компилятором. Альтернатива — класс на вид или интерфейс-стратегия: отвергнуто, различия только в данных (правило «не вводить абстракции спекулятивно»).

**D2. Переименование `Table` → `FurnitureItem`, файлов `table*.ts` → `item*.ts`.**
Хранимое поле `Drawing.furniture.tables` с именем «столы» вводило бы в заблуждение рядом со стулом, поэтому оно становится `items`: `storage.ts` пишет `items`, а читает `items` и, как запасное, `tables`. Старые документы читаются без миграции (`tables` без `kind` → столы). Версия документа не растёт, потому что чтение терпимо к обоим полям; новый документ с `items` старой версией приложения не откроется как с предметами — приемлемо для локального приложения (откат версии не поддерживается и в прошлых changes).

**D3. Вид препятствия — `"furniture"`, слово берётся из вида другого предмета.**
`OBSTACLE_ORDER` заканчивается `"furniture"` вместо `"table"`. `Overlap` получает `otherKind` для пересечений предмет–предмет (для остальных не задан). Плашка (`warning.ts`) собирает слова: сначала препятствия-объекты в прежнем порядке, затем слова видов мебели в порядке каталога без повторов; начало — слово вида, если все пересекающиеся предметы одного вида, иначе «Мебель». При единственном виде текст плашки побитно прежний («Стол пересекается: стена, стол»).

**D4. Значения новых предметов — по виду.**
`tableParams` в `main.ts` становится `Record<FurnitureKind, ItemParams>` с начальными из каталога; панель показывает значения активного вида. Активный вид — состояние инструмента «Мебель» (`furnitureTool`): кнопка вида в панели делает его активным. Идентификаторы DOM: `tool-furniture-<kind>` (кнопки генерируются из каталога при старте, как кнопки образцов материалов стен — существующий образец), поля `furniture-width|length|angle` вместо `table-*`. Существующие тесты разметки (FP-360…367) обновляются под новые идентификаторы только в части переименования; их утверждения о составе и связках остаются в силе.

**D5. История и хранение — без изменений формата записи, кроме имени и `kind`.**
`FurnitureState { items, dimensions }` вместо `{ tables, dimensions }`; ключ истории `furniture` и тип записи не меняются, чтобы сохранённая история читалась. Загрузка истории с полем `tables` принимает его как `items` (те же правила, что в D2).

**D6. Легенда PDF — по видам из каталога.**
`legend.ts` добавляет запись для каждого вида из каталога, чьи предметы есть на странице, после «Гипсокартон» в порядке каталога; образец рисует общий `drawItemSample(kind)` цветом светлой схемы из каталога.

**D7. Тесты по каталогу.**
`furniture-kinds.test.ts` перебирает `FURNITURE_KIND_ORDER` через `it.each`: размеры по умолчанию положительны и угол в [0, 360); цвет различим от подложки/гипсокартона/подсветки и других видов (порог по расстоянию в RGB, как в существующем тесте цвета стола FP-30x); у вида есть название, слово плашки и иконка. Тест «каталог содержит N видов» — единственный, который меняется при добавлении вида, он же показывает вид нового предмета в панели, легенде и плашке.

**D8. Скилл `add-furniture-kind`.**
`.claude/skills/add-furniture-kind/SKILL.md`: чек-лист (1) запись каталога; (2) строка в дельте `furniture-plan` «Каталог видов мебели» (MODIFIED со списком видов); (3) задача в `tasks.md`; (4) обновить тест количества видов; (5) проверить в браузере кнопку, призрак, цвет, плашку, легенду; (6) quality gates. Скилл описывает, как через `/opsx:ff` создать такой change; сам скилл не запускает команды.

## Risks / Trade-offs

- [Переименование полей документа `tables` → `items` ломает чтение документа старой версией] → чтение терпимо к обоим именам; обратная совместимость вперёд не требуется (локальное приложение).
- [Переименование 17 файлов даёт большой diff] → переименование отдельным коммитом-шагом задач, без смены поведения; тесты стола остаются зелёными как проверка эквивалентности.
- [Обобщение до второго вида без самого второго вида скрывает ошибки, видимые только на нём] → тест каталога вместе с тестовым видом, подставляемым в тестах (инъекция каталога в функции, получающие вид); первый настоящий вид — стул — проверит это в отдельном change.
- [Правки тестов стола при переименовании] → меняются только идентификаторы и имена импортов; утверждения о поведении не затрагиваются; каждая правка помечается `// TCR (change furniture-items-catalog): …`.

## Migration Plan

Миграции данных нет: поле `kind` необязательно при чтении, поле `tables` читается как `items`. Откат — `git revert` change.
