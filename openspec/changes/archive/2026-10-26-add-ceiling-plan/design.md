## Context

Мотивация — в `proposal.md`, поведение — в `specs/`. Что в коде уже есть для этого плана:

- Каталог планов и наборы инструментов — `src/plans.ts` (`PLANS`, `PLAN_TOOLS`). Переключатель, страницы PDF и ключи истории строятся по каталогу.
- Стяжка — образец натяжного потолка:
  - `src/rough/screed.ts`: `activeScreeds`, `roomAt`, `addScreed`, `removeScreed`, `setScreedThickness` — привязка к помещению экспликации по опорной точке, «ранний побеждает»;
  - `src/rough/screed-tool.ts`: постановка, выделение по подписи, правка, ластик, через явный `ScreedToolHost`;
  - `src/rough/screed-label.ts`: рамка подписи постоянного экранного размера и попадание в неё.
- Помещения экспликации считаются в `roughScene` как `reconcileRooms(findRooms(mountingScene.walls), drawing.rooms)`.
- Подложка «Мебели» и «Сантехники» — `reconstructionScene` (`src/reconstruction/reconstruction-scene.ts`). План «Сантехника» (`src/plumbing/`) — образец плана поверх «Мебели»: сцена, рабочий набор с объектами только для чтения, отрисовка.
- Рисунки предметов — `drawFurnitureScene` (`src/furniture/furniture-render.ts`).
- Выноски и примечания хранятся по плану через `callout-store.ts` и `notes-store.ts`.
- PDF: `pagesOf` (`src/export/pdf.ts`) даёт страницу на каждый план; легенда — `src/export/legend.ts` (`LegendEntry` — размеченное объединение по `kind`).

## Goals / Non-Goals

**Goals:**
- Натяжной потолок и стяжка используют одну реализацию привязки к помещению; правила «спит / ранний побеждает / делится» не дублируются.
- Мебель на плане не дублируется в данных: её берут из `drawing.furniture` при каждом построении сцены.
- Освещение и выпуск гипсокартона потом добавляются в тот же план без перестройки сцены и хранения.

**Non-Goals:**
- Светильники, выпуск гипсокартона, размеры на плане.
- Изменение поведения стяжки (рефакторинг привязки не меняет её наблюдаемое поведение; тесты стяжки остаются как есть).
- Разделение `main.ts` на модули.

## Decisions

### D1. План в каталоге и инструмент
`{ id: "ceiling", label: "Потолки и освещение" }` встаёт последним в `PLANS`. В `Tool` добавляется `"stretchCeiling"`. Набор плана: `PLAN_TOOLS.ceiling = ["stretchCeiling", "callout", "ruler", "notes", "eraser"]`, первый в списке — инструмент по умолчанию.

Идентификатор плана `ceiling`, а не `ceilings` или `lighting`: план про потолки и освещение, одно короткое слово.

### D2. Модель и хранение
```
StretchCeiling  { id: string; at: Point; dropMm: number }   // dropMm — целое > 0
CeilingContent  { ceilings: StretchCeiling[]; callouts?: Callout[]; notes?: string[] }
Drawing.ceiling?: CeilingContent
```
Поле необязательное, при загрузке не дописывается, версия документа 3 не меняется — как у `plumbing`. Проверка потолка при загрузке отбрасывает некорректные по одному (`drawing-storage`). Порядок списка — порядок постановки, по нему выбирается действующий потолок.

Отклонённые альтернативы:
- Хранить потолок в записи помещения (`drawing.rooms`). Тогда пропал бы режим «спит, пока помещения нет», а слияние и деление помещений пришлось бы решать заново.
- Поле `heightMm` вместо `dropMm`. Отклонено: число — опускание от плиты, а не высота от пола (решение пользователя, вариант A).

### D3. Общая привязка к помещению
Правила привязки стяжки выносятся из `src/rough/screed.ts` в модуль `src/room-anchor.ts`:

```
interface Anchored { id: string; at: Point }
roomAt(p, rooms)                         -> ExplicatedRoom | null
activeAnchored<T extends Anchored>(rooms, list) -> { object: T; item: ExplicatedRoom }[]
canAnchor(rooms, list, p)                -> ExplicatedRoom | null   // помещение под p без действующего объекта
```

`screed.ts` выражает `activeScreeds` и `addScreed` через этот модуль, а `ActiveScreed` и сигнатуры не меняет. Это единственный рефакторинг вне нового плана, и он оправдан правилом «нет дублированной бизнес-логики»: привязка — самая нетривиальная часть обоих объектов.

Отклонённые альтернативы:
- Скопировать `screed.ts` в `src/ceiling/`. Две копии правил, которые обязаны совпадать (спека ссылается на правила стяжки), — со временем разойдутся.
- Сделать потолок разновидностью стяжки (`Screed` с полем `kind`). Тогда смешались бы данные двух планов и их истории.

### D4. Сцена плана
Новый модуль `src/ceiling/ceiling-scene.ts`:

```
ceilingScene(drawing, base = reconstructionScene(drawing)) -> {
  base,                                  // подложка, как у furnitureScene / plumbingScene
  items:    drawing.furniture.items (копии, все виды)
  rooms:    reconcileRooms(findRooms(base.base.walls), drawing.rooms)
  ceilings: activeAnchored(rooms, drawing.ceiling.ceilings)
}
```

Помещения те же, что у `roughScene`: стены «Монтажа», порог экспликации 1 м². Стены гипсокартона помещение не делят, поэтому заливка проходит под ними (см. Risks).

Рабочий набор `openCeiling` / `storedCeiling` (`src/ceiling/ceiling-workspace.ts`) — по образцу `plumbing-workspace.ts`: стены и предметы попадают в `readOnlyIds`, хранимое содержимое — потолки, выноски, примечания.

### D5. Инструмент, подпись, правка
`src/ceiling/ceiling-tool.ts` — по образцу `createScreedTool`: `place`, `select`, `deleteSelected`, `setSelectedDrop`, `setDropOf`, `erase`, `eraseTarget`; хост `CeilingToolHost` явный, без DOM.

Подпись `-50мм` — функция `ceilingLabel(dropMm)` в модели. Рамка и попадание — переиспользование `screedLabelBox`/`screedLabelAt`: функции обобщаются до «текст подписи + точка», чтобы ширина рамки считалась по фактическому тексту. Поле правки на месте и поле панели — тот же DOM-механизм, что у стяжки, с проверкой «целое > 0» без верхней границы. Значение для новых хранится в состоянии сеанса `main.ts`, по умолчанию 50.

Проверка «целое > 0» — одна чистая функция `parseDropMm(text): number | null`, её используют панель, поле на месте и загрузка документа.

### D6. История
Своя история плана по ключу `historyKey(drawingId, "ceiling")`. Запись `{ kind: "ceiling"; ceilings }` — список потолков до операции, по образцу записи «plumbing»; выноски и примечания пишутся своими записями `callouts` и `notes`, как на других планах. Проверка документа истории использует ту же проверку потолка, что загрузка (D2).

### D7. Холст
`src/ceiling/ceiling-render.ts`, слои снизу вверх (`ceiling-plan` «Отображение…»):
1. подложка — та же функция, что у «Мебели» (`drawReconstructionScene`): фон пола, стены, штукатурка, гипсокартон, батареи, коммуникации;
2. предметы — рисунок предмета «Мебели» (`itemDrawingInPlan`, `traceLines`) линиями цвета `muted`, без габаритов, пересечений, рисок и выделения; `drawFurnitureScene` не меняется;
3. заливка `rooms` действующих потолков полупрозрачным цветом `ceiling` схемы (контур без островов, правило even-odd) — в слое `above` подложки после предметов;
4. подписи потолков на непрозрачной подложке цвета бумаги;
5. выноски и примечания.

Потолок висит над помещением, поэтому заливка лежит над подложкой и мебелью, а не под ними. Первый вариант (непрозрачная заливка в нижнем слое) отвергнут: всё, что закрывает пол непрозрачным фоном (заливка помещения, тело батареи, порог в проёме), вырезало бы в жёлтом белые пятна, и картина не соответствует тому, что потолок над мебелью. Полупрозрачная заливка сверху окрашивает и эти участки, а линии стен и мебели видны сквозь неё.

Цвет `ceiling` добавляется в обе схемы `color-theme`: светлая — жёлтый `#ffd600`, тёмная — `#e0b400`. Прозрачность одна — `CEILING_ALPHA = 0.35` в `ceiling-render.ts` (на белом заливка около `#fff1a6`, на тёмном фоне около `#625316`); серые линии под заливкой и подписи над ней читаются. PDF берёт цвет светлой схемы.

Прозрачность рисуется через хук `Translucent` (`alpha`, `paint`): на холсте — `globalAlpha` (`canvasTranslucent`); контекст jsPDF не выводит ни `globalAlpha`, ни альфу `rgba` (проверено: заливка выходит сплошной), поэтому страница PDF и образец легенды передают `pdfTranslucent(doc)` (`src/export/pdf-translucent.ts`) — состояние графики документа `GState` с непрозрачностью заливки. Иконка кнопки в `style.css` — тот же цвет с той же прозрачностью (`--ceiling` в `rgba`).
### D8. PDF и легенда
`pagesOf` даёт восьмую страницу по каталогу; её отрисовка повторяет D7 в миллиметрах листа. Кегль подписи — как у подписи стяжки на странице «Черновые работы». Габариты страницы — объединение габаритов подложки, предметов и выносок (подписи потолков лежат внутри помещений и габариты не расширяют).

Легенда: новый вариант `{ kind: "ceiling"; label: "Натяжной потолок" }` после `drywall`. Записи видов мебели строятся только для страниц «Мебель» и «Сантехника»: на странице потолков у предметов вид подложки, и записи для них не строятся (`pdf-export` «Легенда на странице PDF»).

### D9. Порядок изменений
1. Рефакторинг привязки (D3); тесты стяжки зелёные без изменений.
2. Модель, проверка, хранение, каталог.
3. Сцена, инструмент, холст, `main.ts`.
4. История.
5. PDF и легенда.

## Risks / Trade-offs

- [Помещения считаются по стенам «Монтажа»: кладовка, выгороженная гипсокартоном, не получает своего потолка, заливка проходит под гипсокартоном] → Поведение совпадает со стяжкой и экспликацией. Если понадобятся помещения с учётом гипсокартона, это отдельное изменение для экспликации, а не для потолка.
- [Обобщение `screedLabelAt` и привязки может незаметно поменять поведение стяжки] → Существующие тесты стяжки (`screed.test.ts`, `screed-tool.test.ts`, `rough-render.test.ts`) — контракт; их не меняют, и они должны пройти после шага 1 до остальных шагов.
- [Длинное название «Потолки и освещение» в переключателе] → Сегменты подстраиваются под текст; проверить в браузере при узком окне.
- [Без верхней границы можно ввести опечатку вроде 5000 мм] → Решение пользователя: границы нет. Подпись `-5000мм` сразу видна на плане.
- [`main.ts` растёт ещё на одну ветку плана] → Логика вынесена в `src/ceiling/`; в `main.ts` только подключение по образцу «Сантехники».

## Migration Plan

Миграции нет: поле `Drawing.ceiling` необязательное, старые документы и истории читаются без изменений. Откат — возврат на предыдущую версию кода: `parseStore` перечисляет поля чертежа явно, поэтому старая версия читает документ и отбрасывает поле `ceiling` (потолки теряются при следующем сохранении). Запись истории `ceiling` старая версия считает повреждённой и сбрасывает историю, как при любом повреждении.
