## Context

Наблюдаемое состояние кода (на 2026-10-09):

- `Drawing` (`src/types.ts`) хранит плоско `walls`, `dimensions`, необязательный `doorways`, а также `view` и `scale`. Те же три списка образуют `Scene` в `src/history.ts`; `src/main.ts` держит их в локальных `walls`, `dimensions`, `doorways` и собирает `scene()`.
- Формат документа `version: 3`. Необязательные поля добавлялись без повышения версии (`doorways`, change add-doorway D9): отсутствие — пустое, битое — отбрасывается.
- История: `HistoryStore.histories[drawingId]`, один `DrawingHistory` на чертёж (`drawingHistory()` в `history.ts`; 6 мест вызова в `main.ts`). Формат `version: 2`.
- PDF: `buildPdf(walls, dimensions, unit, scale, format, fontB64, doorways, name, date)` строит один документ из одной страницы; `availableFormats(walls, dimensions, scale, doorways)` и `exportDrawing(...)` — те же позиционные аргументы. Эти сигнатуры используются approved-тестами (около 12 файлов: `pdf.test.ts`, `sheet-pdf.test.ts`, `sheet-fit.test.ts`, `door-pdf.test.ts`, …).
- Approved-тесты строят `Drawing` литералами с полями `walls`, `dimensions` (около 6 файлов: `storage.test.ts`, `history.test.ts`, `*-storage.test.ts`, `auto-dimensions.test.ts`, `room-area.test.ts`) и ожидают, что `parseStore` не добавляет полей, которых не было (сравнение `toEqual` после загрузки).
- Спецификация `pdf-export` уже описывает PDF как «упорядоченный список страниц» и оставляет графу 5 основной надписи пустой.

Ограничение: approved-тесты неизменны (Rule 5). Поэтому рефакторинг идёт аддитивно; он не должен ломать существующие литералы `Drawing`, сигнатуры PDF и формат истории.

## Goals / Non-Goals

**Goals:**
- Единое место, где определено, какие планы существуют (каталог), и тип идентификатора плана.
- Активный план у чертежа, хранение, переключатель в UI, сброс редактирования при переключении.
- Ключ истории на (чертёж, план); обмерочный план использует прежний ключ.
- PDF и подбор форматов принимают упорядоченный список страниц; для одного плана результат побайтово прежний по содержимому.
- Подготовить точки расширения для `demolition-plan`, не вводя того, что ему принадлежит.

**Non-Goals:**
- Сам план «Демонтаж», любые новые виды объектов и инструменты (change `demolition-plan`).
- Перенос `walls`/`dimensions`/`doorways` в новую вложенную структуру `plans`.
- Повышение версии документа хранилища или истории; миграции.
- Название плана в основной надписи (графа 5) и нумерация листов (графы 7, 8): отложено в `TODO.md`.
- Цепочка планов «база следующего = результат предыдущего»: появится вместе со вторым планом.

## Decisions

### D1. Содержимое обмерочного плана остаётся в прежних полях `Drawing`

Вместо перекладывания в `Drawing.plans.measure` (чистая, но ломающая структура) `walls`, `dimensions`, `doorways` остаются как есть и по определению являются содержимым плана `measure`. Новые планы будут добавлять свои необязательные поля (`demolition` в следующем change) рядом.

Обоснование: перекладывание ломает литералы `Drawing` в approved-тестах и формат документа и потребовало бы test-change-request на десятки тестов без изменения наблюдаемого поведения; аддитивные поля — уже принятая в проекте практика. Альтернатива «версия 4 + `plans`» отвергнута как неоправданно рискованная для рефакторинга, который по смыслу не должен менять поведение. Цена: структура неоднородна (один план в «корне», остальные в полях) — скрывается за функциями каталога и сборки страниц (D2, D5).

### D2. Каталог планов — один модуль `src/plans.ts`

```
PLANS: readonly { id: PlanId; label: string }[]   // единственная запись: measure / «Обмерочный план»
type PlanId                                       // литеральный union идентификаторов каталога
DEFAULT_PLAN: PlanId                              // "measure"
isPlanId(value: unknown): value is PlanId
activePlanOf(drawing: Drawing): PlanId            // нормализует: нет поля или неизвестное значение → DEFAULT_PLAN
historyKey(drawingId: string, plan: PlanId): string // measure → drawingId; прочие планы → "<drawingId>:<plan>"
```

Модуль не зависит ни от чего (домен; ни DOM, ни хранилища). `types.ts` импортирует `PlanId`; `Drawing` получает `activePlan?: PlanId`. Идентификатор чертежа — UUID, поэтому суффикс `:<plan>` не может совпасть с чужим ключом.

### D3. Хранение: необязательное поле, отсутствие сохраняется

`parseStore` копирует `activePlan` из чертежа, только если это идентификатор каталога; иначе поле отбрасывается (читается как `measure` через `activePlanOf`). Отсутствие поля НЕ превращается в явное `measure` при загрузке — иначе `toEqual`-сравнения approved-тестов хранилища разошлись бы. Версия документа 3, `isDrawing` не меняется (поле необязательное и не проверяется как обязательное). Переключение плана ставит `dirty = true` и сохраняется общим автосохранением.

### D4. История: ключ на (чертёж, план)

В `history.ts` добавляется `planHistory(history, drawingId, plan)` = `drawingHistory(history, historyKey(drawingId, plan))`. Формат `HistoryStore` (`version: 2`) и валидация не меняются: ключи — произвольные строки. Все 6 вызовов `drawingHistory(historyStore, store.activeId)` в `main.ts` заменяются на `planHistory(historyStore, store.activeId, activePlan)`. Запись закрытия вкладки (`kind: "close"`) попадает в историю активного плана активного чертежа после закрытия — как сейчас, но с ключом плана. Переключение плана не записывается.

Для единственного плана ключ совпадает с прежним, поэтому сохранённая история читается как история обмерочного плана без миграции.

### D5. PDF: страницы как данные, прежние функции — обёртки

В `src/export/pdf.ts`:

```
interface PlanPage { walls: Wall[]; dimensions: Dimension[]; doorways: WallElement[] }
pagesOf(drawing: Drawing): PlanPage[]                 // по странице на план каталога, порядок каталога
availableFormatsForPages(pages, scale): PageFormat[]  // форматы, где помещаются ВСЕ страницы; пустая страница не ограничивает
buildPdfPages(pages, unit, scale, format, fontB64, name, date): jsPDF  // N страниц; рамка и надпись — на каждой
exportPages(pages, unit, scale, format, name): void
```

`buildPdf`, `availableFormats`, `exportDrawing` сохраняют текущие сигнатуры и становятся однострочными обёртками над функциями выше с одной страницей — ради approved-тестов. Производственный код (`main.ts`) использует функции `…Pages`/`exportPages` с `pagesOf(current())`. Страницы строятся одним и тем же кодом: первая страница — конструктор `jsPDF`, остальные — `addPage` того же формата и ориентации; на каждую — `drawSheet` и `drawScene` с размещением по габаритам этой страницы (центрирование в области чертежа, как для одной страницы).

Масштаб, формат, имя и дата общие для всех страниц (спецификация). Подбор формата по всем страницам — пересечение `availableFormats` страниц, а не габариты объединения: каждая страница центрируется независимо.

Кнопка экспорта доступна, если хотя бы одна страница не пуста и есть доступный формат (раньше: «в чертеже есть стены»; для одного плана условие совпадает).

### D6. UI: переключатель планов

В `index.html` вкладки и `#tab-add` оборачиваются в `#tab-row`, `#tabbar` становится колонкой, и вторым рядом под `#tab-row` добавляется `<div id="plan-switch" aria-label="Планы">` (решение пользователя: в одном ряду с вкладками переключатель читался как ещё одна вкладка); кнопки генерируются из `PLANS` (как `renderTabs`), классы стилизуются теми же правилами, что `.unit` и `.unit.active` (общий селектор, без нового вида контрола — `ui.md`). Ширина кнопки подгоняется под подпись (у `.unit` фиксированная ширина 24 px рассчитана на «м/см/мм»). Обработчик клика: `setPlan(id)`.

`setPlan(id)` в `main.ts`: если `id` равен активному — ничего; иначе записать `current().activePlan = id`, выполнить `resetEditing()` (выделение, цепочка, черновик размера, жесты), сбросить инструмент так же, как `activate()` (tool = wall, `syncToolUI`), `dirty = true`, обновить переключатель и кнопки истории, `redraw()`. `activate()` (переключение вкладки) дополнительно синхронизирует переключатель.

Пока в каталоге один план, `setPlan` для чужого идентификатора недостижим; источник сцены (`walls`, `dimensions`, `doorways`) выбирается по активному плану в одной функции — в этом change она всегда возвращает поля обмерочного плана. Это единственное место, которое `demolition-plan` расширит.

### D7. Порядок и границы работ

1. `plans.ts` и тип `Drawing.activePlan` + `storage.ts` (чистые функции, тесты без DOM).
2. `history.ts`: `planHistory`.
3. `pdf.ts`: страницы и обёртки.
4. `main.ts`, `index.html`, `style.css`: переключатель и подстановка `planHistory`/`pagesOf`.

Каждый шаг самостоятелен и проверяется существующим набором тестов (регрессия) плюс новыми.

## Risks / Trade-offs

- **Неоднородная структура (D1).** Один план «в корне», остальные — в полях. Смягчение: доступ только через каталог и функции сборки; решение о переносе в `plans` можно принять позже отдельным change с миграцией.
- **Пустой каталог из одного плана делает часть требований «пустыми» для проверки** (переключение между планами, история разных планов). Смягчение: чистые функции (`historyKey`, `pagesOf`, `buildPdfPages` на двух страницах, `availableFormatsForPages`) покрываются тестами с искусственными входами; UI-поведение переключателя проверяется вручную в браузере (DOM-стенда в проекте нет, см. `TODO.md`).
- **Обёртки `buildPdf`/`availableFormats`/`exportDrawing` остаются ради approved-тестов.** Это не мёртвый код, но дублирование API; убрать можно через test-change-request отдельно.
- **Общий формат при разных габаритах страниц.** Страницы разного размера на одном листе формата A4/A3 — допущено спецификацией («все страницы одного формата»); следствие: страница с мелким планом занимает тот же лист, что и крупная.
- **Ключ истории `"<id>:<plan>"`.** Закрытый чертёж оставляет в `histories` ключи всех своих планов; так же сейчас остаётся ключ чертежа. Утечка в localStorage ограничена `HISTORY_LIMIT`.
- **Совместимость.** Старые документы и истории открываются без миграции; документ с `activePlan` открывается и старой версией приложения (поле игнорируется).
