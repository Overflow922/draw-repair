## Context

- Проёмы реализованы в `src/doorway/` (change `add-doorway`, архив 2026-10-06): чистые модули `doorway-faces` (свободные участки граней `faceRuns`, расстояния, нарушение), `doorway-edit` (установка, ввод, сдвиг), `doorway-guard` (ограничение правок и рисования стен), `doorway-layout` (вырез, контур, цепочки, подпись), `doorway-scene` (попадание, рамка, ластик, каскад) и DOM-адаптер `doorway-tool`. `main.ts` хранит `doorways` активного чертежа и набор выделенных проёмов и маршрутизирует события.
- Тип `Doorway { id, wallId, anchor, offsetCm, widthCm, heightCm }`; `Drawing.doorways?` и `Scene.doorways?` (история) — отсутствие поля = пустой список; JSON-ключ — `doorways`.
- Одобренные тесты `add-doorway` неизменяемы и фиксируют публичный API: литералы `Doorway` без поля вида и сравнение результатов через `toEqual` (`placeDoorway` → `{ id, wallId, anchor, offsetCm, widthCm, heightCm }`, `DE-HEIGHT`, roundtrip хранения); сигнатуры `placeDoorway`, `setDistance`, `setWidth`, `setHeight`, `slideDoorway`, `arrowSlide`, `doorwayDistances`, `doorwayHolds`, `faceRuns`, `jambsT`, `violatesDoorways`, `thicknessAllowed`, `hitDoorway`, `doorwaysInRect`, `wallsInRect`, `erasePick`, `deleteObjects`, `drawScene`/`RenderOptions.doorways`, `EditMode.doorways`, `ChainInput.doorways`; `faceRuns` проверяется как функция только стен.
- Мутационного тестирования в проекте нет; тесты — `vitest`.

## Goals / Non-Goals

**Goals:**
- Окно — второй вид элемента стены без дублирования логики: инвариант, ограничения, правка, сцена и история работают с объединением видов (D1, D3).
- Соседние элементы — стыки граней одним дополнением к свободным участкам граней (D2); запрет пересечения не требует отдельного механизма ни в правке элемента, ни в ограничителе правок стен.
- Совместимость: старые документы, история и одобренные тесты проёмов не меняются (D1, D7).
- Отличия окна (данные, инструмент, обозначение, подпись) — переключение по виду в небольших модулях (D4–D6).

**Non-Goals:**
- Двери и дуги открывания (вид элемента добавляется позже по образцу D1).
- Переименование модуля `src/doorway/` и capability `doorway`.
- Высота потолка, проверка «подоконник + H».

## Decisions

### D1. Модель: объединение с видом по умолчанию

`types.ts`:

```text
Doorway    { kind?: "doorway"; id; wallId; anchor: "a" | "b"; offsetCm; widthCm; heightCm }
WallWindow { kind: "window";   id; wallId; anchor: "a" | "b"; offsetCm; widthCm; heightCm; sillCm }
WallElement = Doorway | WallWindow
Drawing.doorways?: WallElement[]        (JSON-ключ прежний)
Scene.doorways?:   WallElement[]
```

Вид проёма — отсутствующее поле или `"doorway"`; сужение по `e.kind === "window"`. Это всё ещё размеченное объединение, но вариант по умолчанию не требует поля, поэтому:
- литералы `Doorway` в одобренных тестах и результат `placeDoorway` (`toEqual` без `kind`) остаются верными;
- формат сохранённого проёма не меняется: старые документы и снимки истории читаются как есть, старая сборка читает новый документ (окно — как проём, теряя подоконник).

Имя `WallWindow` — чтобы не затенять глобальный DOM-тип `Window`. Поле и ключ `doorways` не переименовываются: ключ закреплён форматом и тестами; в коде поле документируется как «элементы стены».

Альтернатива — обязательный `kind` у всех: чище, но ломает одобренные тесты (`toEqual`) и требует test-change-request без выигрыша в поведении.

### D2. Соседние элементы — стыки граней

`doorway-faces`:

```text
faceRuns(host, walls, side)                        — без изменений: только стены
elementRuns(host, walls, elements, side, self)     = faceRuns − ⋃ [j1, j2] других элементов на host
doorwayDistances(d, walls, elements = [])          — по elementRuns
doorwayViolation(d, walls, elements = [])          — наибольшее отрицательное расстояние
doorwayHolds(d, walls, elements = [])
```

«Другие» — элементы с `wallId === host.id` и `id !== self.id` (призрак и правка получают свежий/тот же `id`). Вычитание участков соседей режет свободный участок грани на откосах соседа; выбор участка элемента (`runOf`, наибольшее перекрытие) остаётся прежним, поэтому:
- расстояние до соседа — от откоса до ближнего откоса соседа на обеих гранях;
- при наложении участок элемента обрезан откосом соседа, расстояние отрицательно и равно по модулю длине наложения (spec `doorway` «Стыки грани…»);
- инвариант «все расстояния ≥ 0» включает непересечение — отдельной проверки нет.

`elements` — необязательный последний параметр (по умолчанию `[]`), чтобы сигнатуры, зафиксированные одобренными тестами, не менялись. Все вызовы в продакшн-коде передают список явно; риск «забыть список» закрывается тестами на соседей через каждую публичную операцию (test-plan).

### D3. Операции над элементом — общие для видов

`doorway-edit` работает с `WallElement` и сохраняет вид и данные вида (`{ ...e, ... }`):
- `freeIntervals` строится по `elementRuns` обеих граней;
- `placeDoorway(host, walls, cursor, width, height, id, elements = [])` и новая `placeWindow(host, walls, cursor, width, height, sill, id, elements)` — общий внутренний расчёт положения призрака; проём создаётся без поля `kind`, окно — с `kind: "window"`;
- `setDistance`, `setWidth`, `slideDoorway`, `arrowSlide` — добавлен последний параметр `elements = []`; `setHeight` — без изменений; новая `setSill(w, value)` (`value ≥ 0`, иначе `invalid`);
- тип результата — `ElementEdit<E extends WallElement> = { kind: "applied"; doorway: E } | { kind: "rejected"; reason }`, `DoorwayEdit = ElementEdit<Doorway>` сохраняется для тестов;
- уже нарушенный элемент (наложение из документа): допустимый диапазон сдвига расширяется до текущего положения, чтобы сдвиг в сторону нарушения оставлял элемент на месте, а не перебрасывал его через допустимый диапазон (spec `doorway` «Наложение из документа не углубляется»);
- стрелки по нескольким элементам на одной стене — чистая `nudgeElements(selected, walls, elements, arrow, step)`: элементы обрабатываются по убыванию проекции на направление сдвига (ведущий — первым), каждый — с уже обновлённым списком; пара в касании сдвигается вместе. `doorway-tool` `nudge` вызывает её вместо цикла по выделенным.

### D4. Инструмент «Окно»

Конфигурация вида — чистый модуль `src/doorway/element-kind.ts`: `elementDefaults(kind)` и `acceptField(kind, field, cm)` (тестируются без DOM). `doorway-tool` параметризуется видом: `createElementTool(kind, host, panel)` с этой конфигурацией — поля панели (`width`, `height` и для окна `sill`), значения по умолчанию (90/210 или 120/150/85 см), валидация полей (`> 0`; подоконник `≥ 0`), фабрика призрака (`placeDoorway` / `placeWindow`). Общее поведение — призрак, клик, нажатие на элемент любого вида, перетаскивание, стрелки, поле ввода числа — одно.

Контракт адаптера (заменяет `createDoorwayTool` / `DoorwayToolHost`; тестируется в node с заглушками хоста и полей — хост явный, DOM нужен только полю ввода на месте числа):

```text
createElementTool(kind: "doorway" | "window", host: ElementToolHost, panel: ElementPanel): ElementTool
ElementToolHost — как DoorwayToolHost, но:
  elements(): readonly WallElement[]            (вместо doorways(): все элементы чертежа любого вида)
  selectedElements(): readonly WallElement[]    (вместо selectedDoorways())
  add(e: WallElement) ; replace(prev: WallElement, next: WallElement) ; select(e: WallElement)
ElementPanel { root: HTMLElement; width: HTMLInputElement; height: HTMLInputElement; sill?: HTMLInputElement }
  поле применяется по событию "change"; поле sill есть только у окна
ElementTool — прежний DoorwayTool; ghost(): WallElement | null
```

Каждый вызов операций D2/D3 в адаптере передаёт `host.elements()`: призрак, цепочки чисел и попадание по числу, ввод числа, поля панели, перетаскивание; стрелки — через `nudgeElements`. Поле панели при выделенном элементе своего вида меняет его, иначе — параметры новых элементов (с проверкой `acceptField`).

`main.ts`: второй экземпляр инструмента, кнопка «Окно» после «Проём», панель `#window-panel` в `index.html`. Выделение одного элемента открывает панель инструмента его вида (`syncPanel` показывает значения выделенного элемента только своего вида). Хост инструмента получает `elements()` вместо `doorways()` — все элементы чертежа, независимо от вида; `selectedDoorways` — выделенные элементы любого вида.

### D5. Обозначение окна

`doorway-layout` — новая чистая функция `windowLines(w, walls, elements)` в мировых координатах:

```text
T = толщина host,  [j1, j2] = jambsT,  s = 0.6·T
faces  : грани ±T/2 на [max(j1, run0), min(j2, run1)]       — линии контура
jambs  : как openingLines                                    — линии контура
squares: [j1, j1 + s] × [−s/2, s/2],  [j2 − s, j2] × [−s/2, s/2]  — контур
glass  : lat = ±T/6 на [j1 + s, j2 − s], только если j2 − j1 > 2·s  — тонкие линии
```

Квадраты и стёкла считаются в рамке оси (`hostPoint`), поэтому не зависят от направления стены и стороны привязки. Отсечение по видимым граням нарушенного элемента — как в `openingLines`. `render.ts` `drawDoorways` выбирает `openingLines` или `windowLines` по виду; вырез тела (`cutPieces`, `cutContour`) общий для всех элементов. Толщина тонких линий — `m.hatchPx`, цвет — `p.ink` (проём рисует продолжения граней `p.muted`).

### D6. Подпись окна

Сторона и точка — `heightLabelSide` / `heightLabelAt` без изменений. Текст из двух частей: «H=…» цветом `p.ink`, «H под.=…» — новым цветом палитры `p.sill` (синий; светлая и тёмная темы), между частями два пробела. Рамка — прямоугольник (без скругления; радиус — открытый вопрос в TODO.md) по оценке ширины текста (тот же приём `0.6·labelPx` на символ, что у подписи проёма, — `measureText` jsPDF не даёт единиц листа), линия `p.ink`, `m.hatchPx`. `export/pdf.ts` `wallsBBox` учитывает ширину подписи окна (длиннее подписи проёма).

**Ориентация подписи (проём и окно).** Подпись рисуется в повёрнутой системе координат: `translate(центр)`, `rotate(θ)`, текст и рамка — относительно центра. θ — угол направления оси `d` на экране (`d` — единичный `a → b`). Стена вертикальна, если `|d.x| ≤ RIGHT_SIN` (допуск прямого угла 0.5°): тогда направление переворачивается (`θ + π`) при `d.y > 0`, и текст читается снизу вверх. Иначе направление переворачивается при `d.x < 0` — текст идёт слева направо, не вверх ногами. Центр отодвигается от грани по нормали на полосу цепочек плюс половину высоты подписи (с полем рамки): текст параллелен стене, поэтому вдоль нормали подпись занимает только свою высоту. `wallsBBox` для окна учитывает повёрнутый прямоугольник подписи (его четыре угла); подпись проёма, как и раньше, — точка у грани.

**Рамка у подписи проёма.** Подпись проёма обводится той же рамкой, что подпись окна (`p.ink`, `m.hatchPx`, поле `LABEL_FRAME_PAD`), текст одной части — по центру рамки. Подпись описывается как `ElementLabel { parts }`, рамка есть всегда. В `wallsBBox` подпись проёма по-прежнему учитывается точкой у грани (она короче подписи окна; одобренный DP-03 закрепляет габариты по x).

### D7. Хранение и история

`storage.ts` / `history.ts`: валидатор `isWallElement` = проём (`kind` отсутствует или `"doorway"`; прежние правила `isDoorway`) или окно (`kind === "window"`, прежние правила + конечный `sillCm ≥ 0`). Неизвестный `kind` — не элемент. При загрузке чертежа такие элементы отбрасываются (как сейчас битые проёмы); в снимке истории нарушают структуру (как сейчас битый проём в снимке). Нормализация при загрузке копирует поля по виду (`kind` и `sillCm` только у окна), поэтому roundtrip проёма без `kind` остаётся побайтно прежним. Версии документа и истории не меняются.

### D8. Ограничение правок стен и рисования

`doorway-guard` уже получает полный список элементов (`EditMode.doorways`, `violatesDoorways(before, after, doorways)`, `thicknessAllowed`, `ChainInput.doorways`). Нарушение каждого элемента считается `doorwayViolation(d, walls, list)` — со стыками-соседями (D2), поэтому сближение элементов с разными сторонами привязки при укорочении стены ограничивается тем же поиском касания (бисекция), что и стык в проёме; «не углублять» сравнивает нарушение до и после, включая наложения. Сигнатуры не меняются.

### D9. Модули

```text

src/doorway/doorway-faces.ts     elementRuns, расстояния/нарушение со списком элементов (D2)
```

Зависимости прежние: `doorway-tool` → `doorway-edit` → `doorway-faces` → `wall-geometry`; домен без DOM.

## Risks / Trade-offs

- **Необязательный параметр `elements`.** Вызов без списка молча игнорирует соседей. Смягчение: все продакшн-вызовы передают список; тесты на соседей идут через операции инструмента и ограничителя, а не только через `doorway-faces`.
- **Стоимость.** `elementRuns` добавляет вычитание интервалов к `faceRuns` — линейно по числу элементов на стене; заметного роста к ~14 мс шага (TODO) не ожидается.
- **Необязательный дискриминант.** `kind?` у проёма — сужение работает только через `kind === "window"`; проверка `kind === "doorway"` была бы ошибкой. В коде использовать предикат `isWindow(e)`.
- **Старая сборка** читает окно как проём и при сохранении теряет `kind`/`sillCm`. Приложение разворачивается целиком — принимаем, как в `add-doorway`.
- **Узкие окна.** При ширине ≤ 1.2·T квадраты перекрываются или касаются; стёкла не рисуются (spec). Внешний вид при ширине < 0.6·T — квадраты выходят за участок — допускается как вырожденный случай.
- **Синий в PDF.** Цветная часть подписи в ч/б печати становится серой; приемлемо, рамка и текст остаются читаемыми.

## Migration Plan

Миграции нет: документы и история версий без окон читаются без изменений (проём без `kind`). Откат: старая сборка читает окна как проёмы.
