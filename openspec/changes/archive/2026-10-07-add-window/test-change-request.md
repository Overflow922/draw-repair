# Test Change Request — add-window

Статус: **решён пользователем 2026-10-06** — оба предложенных изменения приняты (TCR-1: добавить `sill` в theme.test.ts; TCR-2: тип помощника → `WallElement[]`). Реализация была остановлена (CLAUDE.md Rule 5) после задач 1.1–4.1 и 6.2. Изменённые тесты повторно валидируются: см. test-validation.md, ревизия 5.

## TCR-1. `src/theme.test.ts` — точный набор ключей палитры

**Тесты:** `LIGHT-EXACT-1` (светлая палитра `toEqual` фиксированному объекту), `DARK-KEYS-1` (ключи тёмной палитры равны фиксированному списку `KEYS`).

**Конфликт:** одобренные тесты `add-window` требуют цвет подоконника в палитре — `LIGHT_PALETTE.sill`, `DARK_PALETTE.sill` (WL-07, WL-07c, WP-01; design D6: «новым цветом палитры `p.sill` (синий; светлая и тёмная темы)»). Любое новое поле палитры ломает `LIGHT-EXACT-1` и `DARK-KEYS-1`, хотя прежние цвета не меняются. Спецификация (`window` «Подпись окна») требует синий цвет части «H под.», то есть палитра расширяется намеренно.

**Предлагаемое изменение:** добавить `sill: "#2b7fd4"` в эталон `LIGHT-EXACT-1` и `"sill"` в список `KEYS` (`DARK-KEYS-1` уже проверяет формат цвета каждого ключа). Остальные проверки не меняются; прежние цвета закреплены, как и раньше.

**Альтернатива без правки theme.test.ts:** брать синий из существующего `p.angle` (#2563eb / #60a5fa — цвет угла построения и линейки). Тогда меняются новые тесты WL-07, WL-07c, WP-01 (`.sill` → `.angle`) и design D6; цвет подписи окна становится связан с цветом угла построения.

## TCR-2. `src/doorway/doorway-storage.test.ts` — аннотация типа в помощнике

**Место:** строка 77–80, помощник `doorwaysOf(e: HistoryEntry | null): Doorway[]`, возвращает `e.doorways ?? []`.

**Конфликт:** по design D1/D7 снимок истории хранит элементы стены любого вида: `HistoryEntry.doorways?: WallElement[]`. `WallElement[]` не присваивается `Doorway[]`, поэтому `tsc --noEmit` падает на этом тестовом файле (во время выполнения тесты проходят; проверки не затронуты).

**Предлагаемое изменение:** только тип возврата помощника — `Doorway[]` → `WallElement[]` (и импорт `WallElement`). Ожидания и данные тестов DH-* не меняются.

**Альтернатива без правки теста:** изменить design D1 — `Doorway` становится псевдонимом объединения (`type Doorway = WallElement`), а вариант проёма получает новое имя. Литералы в одобренных тестах остаются верными, но имя `Doorway` в коде перестаёт означать «проём», что запутывает модель.

Изменённые тесты повторно валидируются (test-validation, новая ревизия) до продолжения реализации.

## TCR-3. `src/doorway/window-render.test.ts` — WL-03b и WL-05 принимают рамку подписи за линии окна

Статус: **решён пользователем 2026-10-06** — принят вариант «сузить тесты».

**Конфликт:** рамка подписи окна (spec window «Подпись окна»; design D6 — линия `p.ink`, `m.hatchPx`) — тонкая горизонтальная линия чернил. WL-03b (зум 4) и WL-05 (окно у торца стены) отбирают все тонкие горизонтальные линии чернил в диапазоне x и засчитывают рамку как стекло / как рисунок за торцом стены. Валидатор этого не видел: до реализации рамки не было.

**Изменение:** в WL-03b и WL-05 тонкие линии учитываются только в полосе толщины стены (|y| ≤ T/2 + допуск), где обязаны лежать линии окна. Ожидания по стёклам, квадратам и граням не меняются. Повторная валидация: test-validation.md, ревизия 6.
